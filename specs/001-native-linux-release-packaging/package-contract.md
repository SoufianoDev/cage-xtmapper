# Shared Package Payload Contract — Cage XtMapper

**Status:** documented from the active branch's shared payload generator and target package candidates. This contract does not imply runtime support or public release publication.

## Payload identity and validation

All current native package adapters consume the common payload generated by the release packaging tool; they do not build an independent application ELF in the package adapter.

Every adapter must validate before creating a package:

1. Requested package version equals the version in manifest.json.
2. Manifest target architecture matches the architecture expected by the target package manager.
3. The executable exists and is executable.
4. Actual executable SHA-256 equals the ELF SHA-256 recorded in the manifest.
5. Source commit identity is preserved in the manifest/provenance or package metadata.
6. The final artifact receives a SHA-256 sidecar. The checksum verifies integrity, not publisher authenticity.

Target build artifacts retain build-info.json, provenance.txt, manifest.json, ELF reports, Meson dependency/build-option introspection, Ninja link commands and installed-package inventory. The per-target environment.txt records source commit, workflow SHA, workflow run ID, architecture, image digest and observed OS identity.

CI-generated package versions (for example, Debian/Ubuntu's 0.0.0-ci<run-id>) are diagnostic candidate versions. They are not official release versions and must not be attached to a tagged release as though they were.

## Package-owned paths

| Item | Contract |
|---|---|
| Main executable | /usr/bin/cage-xtmapper |
| Documentation and manifest | /usr/share/doc/cage-xtmapper/README.md and manifest.json where the format uses the standard documentation directory |
| License and notice files | /usr/share/licenses/cage-xtmapper/ for RPM, Arch and Alpine candidates; Debian places the component notice files in its package documentation area |
| Persistent configuration / user data | No package-owned system configuration or user-data path is declared by these candidates. Do not invent a package-owned configuration file. |
| Shared libraries | No shared .so files are currently bundled. Native packages depend on system libraries generated/validated using their ecosystem tools. |
| Checksums / audit metadata | SHA-256 sidecars and retained CI audit artifact; public release attachment is a separate, not-yet-implemented step for native packages. |

The portable payload uses the same executable/manifest/license identity and contains no shared library bundle. It is a candidate archive only; the archive integrity check is not an application runtime test.

## Native adapters and dependency policy

- **Debian / Ubuntu:** validate manifest version/architecture/ELF SHA, install the executable under /usr/bin, store manifest and notices under package documentation, derive Depends through dpkg-shlibdeps, preserve source commit and ELF SHA in package metadata, and create a package checksum.
- **Fedora RPM:** validate manifest version/architecture/ELF SHA, use automatic RPM SONAME/symbol requirements, install the executable and documentation/licenses under /usr, and create a checksum sidecar.
- **Arch Linux:** validate manifest and executable SHA, use a target-built PKGBUILD and target package ownership mapping for runtime dependencies, install the executable/documentation/licenses under /usr, and create a checksum sidecar.
- **Alpine:** build against musl in an Alpine environment, validate manifest/version/architecture/SHA, generate APK so: runtime dependencies from the built ELF, and create a checksum sidecar. The current test signs with an ephemeral CI key trusted only within the audit container; this is not a production signing scheme.
- **Portable archive:** generated from the common release payload. Current archives include executable, manifest, SHA-256 list and required component notices/licenses, but no .so runtime bundle.

## Legacy installer ownership boundary

The existing bootstrap manages /opt/cage-xtmapper and /usr/local/bin/cage-xtmapper. Native package candidates use /usr/bin/cage-xtmapper and do not claim ownership of the bootstrap paths. The current package pre-install guards refuse installation when the legacy tree or launcher exists, because /usr/local/bin can shadow /usr/bin.

This is a protective conflict check, not a migration implementation. Existing files are not removed or silently transferred. Migration, rollback/recovery, coexistence and preservation of modified/unowned files still require dedicated lifecycle tests before native packages become the default installation method.

## Non-goals and external prerequisites

The packages do not install, update or redistribute Waydroid or the XtMapper Android APK. They do not create production signing keys or publish signed repositories. Runtime still depends on a suitable Wayland/compositor and graphics/input/seat environment, Waydroid and the XtMapper APK, correct device permissions and the required privilege/transport path.
